# kotlin-ecshopx 架构设计文档

> 版本：v1.0（2026-10-14）
> 输入：`thirdparty/ECShopX`（Lumen 8 + Dingo API + Doctrine ORM，PHP 8.2）源码静态分析
> 配套文档：[概要设计](./02-概要设计文档.md) · [详细设计](./03-详细设计文档.md) · [URL 列表](./04-URL列表文档.md) · [全量路由附录](./附录-ECShopX全量路由清单.md) · [开发步骤](./05-开发步骤-M0M1M2-P0P1P2.md)

## 1. 背景与目标

ECShopX 是一套 SaaS 多租户电商系统：50 个业务 Bundle、476 个 Doctrine 实体、约 2199 个 HTTP 端点（后台 1392 / 消费者端 579 / 员工端 114 / 超管 61 / 对接与回调 53）。本项目将其核心能力重写为 **Kotlin + Spring Boot** 版本，目标：

1. 保留源系统的**商业模型与接口契约**（URL、入参出参、`{"data":…}` 包络、分单位金额、Unix 秒时间戳），做到前端（小程序/H5/PC）几乎无感迁移；
2. 架构上**收敛复杂度**：50 Bundle → 6 个 Maven module；放弃 Dingo 动态路由装载、运行时 guard 切换等 PHP 特有机制；
3. **单机可部署**：嵌入式数据库（选型 H2，见 §6），一个 fat-jar + 一个数据文件即可运行，便于学习与小型生产；
4. 分期交付：M0/M1/M2 里程碑对应 P0/P1/P2 接口优先级（见 [开发步骤](./05-开发步骤-M0M1M2-P0P1P2.md)）。

**不在范围内**（P2 或明确裁剪）：跨境清关、医药处方、酷家乐/数云/有数等第三方生态、微信支付服务商分账（AdaPay/BsPay/银商/汇付/工行渠道）、Kafka、Swoole WebSocket——保留扩展点，不迁移实现。

## 2. 源系统架构摘要（迁移对照基准）

```
bootstrap/app.php → AppKernel(Lumen)
  ├─ Dingo API: $api->version('v1') 不占 URL 段，前缀恒为 /api
  ├─ bootstrap/route.php: 按 URL 第 2 段懒装载路由文件（api|admin|h5app|wxapp|superadmin|…）
  ├─ 鉴权: Dingo provider(jwt|wxapp|adminwxapp|superadmin…) + Lumen guard 运行时切换
  ├─ 持久化: Doctrine ORM 注解实体(src/*/Entities)，单 manager 'default'，无物理外键
  ├─ 响应: Fractal ResultArraySerializer → {"data": …}；AppKernel 把非 200/401 状态改写为 200
  └─ 异步: Redis/RabbitMQ queue + 每分钟 cron + Swoole websocket
```

对 Kotlin 版必须原样保留的**行为契约**：

| 契约 | 源系统行为 | Kotlin 版决策 |
|---|---|---|
| 响应包络 | 一律 `{"data": …}` | 保留，`ApiResponse<T>` 统一封装 |
| 错误状态码 | 除 401 外全部 HTTP 200，错误放 body | **改为标准 HTTP 状态码**（400/401/403/500），body 结构不变；网关兼容层可配置回退 200 |
| 列表载荷 | `{"data":{"total_count":N,"list":[…]}}` | 保留 |
| 分页参数 | `page` + `pageSize`（部分 `page_size`） | 保留双写法兼容 |
| 金额 | 整数分（BIGINT） | 保留，Kotlin 侧 `Long`，DTO 层不出现在浮点 |
| 时间 | Unix 秒 INTEGER | 保留 `Long`；工具类互转 `Instant` |
| 业务单号 | order_id/trade_id/refund_bn 应用层生成 | 号段生成器 `SeqGenerator`（`seq_generator` 表 + 乐观锁） |
| 多租户 | 全表 `company_id`，独立部署固定 =1 | 保留列 + `TenantFilter` 注入 |

┌───────────────▼────────────────────────────────────────────┐

│  │ service 层 领域服务 + 编排 + @Transactional 边界        │  │

│  │ dao 层    MyBatis Mapper + 分页拦截器 + 号段生成器      │  │

│  │ common   响应包络/错误码/DTO/工具/常量                  │  │

技术栈一览：

| 关注点 | 选型 | 对应 PHP |
|---|---|---|
| 语言/框架 | Kotlin 2.x + Spring Boot 3.x（JDK 17） | PHP 8.2 + Lumen 8 |
| API 框架 | Spring MVC（`@RestController`） | Dingo API |
| 鉴权 | Spring Security + jjwt；多 FilterChain 对应多 provider | tymon/jwt-auth + Dingo providers |
| ORM/DAO | **MyBatis 2.x（Kotlin 接口 Mapper）**，无关联注解，逻辑外键 | Doctrine ORM（同为"实体=表、无关联"风格，迁移心智一致） |
| 分页 | 自研 `PageQuery/PageResult` + MyBatis 拦截器（详见[详细设计 §4](./03-详细设计文档.md)） | Repository 手写 offset+count |
| 事务 | Spring `@Transactional` + `TransactionTemplate` Kotlin DSL | DBAL beginTransaction/commit/rollback（171 个文件、718 处） |
| 校验 | jakarta.validation 注解 + `@Validated` | `app('validator')->make` 内联校验 |
| 缓存 | Caffeine（进程内）+ 可选 Redis profile | 6 个逻辑 Redis connection |
| 定时任务 | `@Scheduled` | `Espier\Console\Kernel` everyMinute |
| 消息/异步 | Spring `ApplicationEvent` + `@Async`（进程内）；MQ 留扩展点 | queue/Jobs/Kafka/WebSocket |
| 构建 | Maven 多 module（见 §5） | composer |

## 4. API Surface 与鉴权架构

源系统 6 类入口按"URL 段 → 路由文件 → guard"动态分发；Kotlin 版固定为 4 个 Surface，各自独立 `SecurityFilterChain`：

| Surface | 基址 | 源 provider | 身份载体 | Principal 内容 |
|---|---|---|---|---|
| 商家/运营后台 | `/api/**`（排除以下前缀） | `jwt` | Bearer JWT | operatorId, companyId, operatorType, distributorIds |
| 店铺员工端 | `/api/admin/wxapp/**` | `adminwxapp` | `x-wxapp-session` 头 | salesmanId, distributorId, shopIds |
| 消费者端 | `/api/h5app/**`、`/api/wxapp/**` | `wxapp`/公开 | Bearer JWT（会员） | userId, companyId, openId |
| 平台超管 | `/api/superadmin/**` | `superadmin` | Bearer JWT | superAdminId |

回调类（微信授权事件、支付 notify）是无鉴权白名单路由，单独一组 `WebhookController`。

权限模型沿用源系统"**路由别名 ↔ 资源 code**"方案：`as = goods.items.lists` 映射 `resources.resource_code`，`activated` 中间件在 PHP 里同时做权限、租户激活校验和"当前选中店铺"解析——Kotlin 版拆为三个正交组件：

```
JwtAuthenticationFilter（认证）
  → TenantFilter（company_id 注入 + 激活校验，独立部署恒 1）
    → CurrentShopResolver（会话选中店铺，源为 Redis key select_distributor{op}-{co}，Kotlin 用登录态+请求参数 distributor_id 覆盖）
      → @RequiresResource("goods.items.lists") 方法注解 + AOP（权限校验，替代 activated 的 checkPermission）
```

## 5. Maven 多 module 设计

```
kotlin-ecshopx/                      (parent, packaging=pom)
├── pom.xml                          依赖 BOM：spring-boot 管理版本 + kotlin 插件配置
├── ecshopx-common/                  无 Spring 依赖优先：
│     ApiResponse/PageQuery/PageResult/ErrorCode/业务常量(状态枚举)
│     Money(分)工具、TimeSec 工具、SeqNo 号段接口、公共 DTO
├── ecshopx-dao/                     依赖 common + mybatis-spring-boot-starter
│     dataobject(DO，与表 1:1)、mapper(接口 + XML)、分页拦截器、
│     数据源/H2 配置、schema.sql/seed.sql 资源
├── ecshopx-service/                 依赖 dao + common
│     领域服务(items/cart/order/trade/aftersales/member/promotion/distributor…)
│     @Transactional 编排、状态机(订单/售后)、领域事件发布、号段实现
├── ecshopx-web-admin/               后台+员工端+超管 Controller，依赖 service
├── ecshopx-web-front/               消费者端 Controller + Webhook，依赖 service
└── ecshopx-boot/                    依赖两个 web module；@SpringBootApplication、
      全局配置(yml)、打包 spring-boot-maven-plugin → fat-jar
```

依赖方向（严格单向，禁止反向/跨层）：

```
web-admin ─┐
           ├─> service ─> dao ─> common
web-front ─┘
boot ─> (web-admin, web-front)
```

设计要点：

1. **web 按 Surface 分 module**：消费者端与后台的 DTO/鉴权/限流差异大，分 module 后 P0 可只部署 front+admin 的核心包；
2. **service 内部按领域分包而非再拆 module**：领域间存在编排依赖（下单要用商品+促销+会员），拆 module 会造成环；M2 若需要插件化再评估；
3. dao 只出 DO，service 出领域模型/BO，web 出 VO——三层对象隔离，转换函数集中在各层 `converter` 包；
4. 版本与仓库：parent 统一 `${revision}`，仓库源用阿里云镜像（settings.xml 已在环境配置）；
5. 测试布局：dao 层 H2 内存库 + `@MybatisTest`，service 层 Mockito，web 层 MockMvc；`ecshopx-boot` 聚合 JaCoCo 报告。

parent pom 关键骨架：

## 6. 数据库选型：H2（对比 SQLite）

| 维度 | H2（选定） | SQLite |
|---|---|---|
| 驱动 | 纯 Java，无 native | xerial 需加载本地库 |
| 与 Maven/JDBC 生态 | 一等公民，Spring Boot 内建支持、内存模式单测零配置 | 可用但类型映射粗糙（无真正 BIGINT/DECIMAL 语义） |
| MySQL 兼容模式 | `MODE=MySQL`，DDL 可直接沿用 MySQL 方言，未来平滑切 MySQL | 方言差异需改写 |
| 并发写 | 行级锁（MVStore），多实例需换 Server/Tika 模式 | 库级写锁，单写者 |
| 部署形态 | 文件模式 `./data/ecshopx.mv.db`，同 SQLite 一样简单 | 文件 |

结论：**H2 2.2，`jdbc:h2:file:./data/ecshopx;MODE=MySQL;DATABASE_TO_LOWER=TRUE`**。SQLite 仅在"极致瘦身/嵌入式客户机"场景作为 profile 备选（DAO 层 SQL 保持 ANSI 子集即可切换）。表结构以源系统 Doctrine 注解为准：70 张核心表覆盖 10 个域（详见 [概要设计 §6](./02-概要设计文档.md) 与 [`sql/schema.sql`](../sql/schema.sql)）。金额 BIGINT 分、时间 BIGINT 秒、JSON 一律 CLOB、无物理外键、全表 `company_id`。

升级路径：数据量超出单机 H2 时，同一套 DDL 直接落 MySQL 8（schema.sql 保持 MySQL 方言子集），应用侧仅换 datasource profile。

## 7. 事务支持设计（Kotlin）

源系统 718 处 `beginTransaction/commit/rollback` 集中在 service 编排层，Kotlin 版映射为**声明式为主、模板式为辅**：

- 规则 1：跨表写编排方法标 `@Transactional`（Spring proxy，配合 kotlin-spring 插件使类/方法自动 open）；约定 `Isolation.READ_COMMITTED` + `REQUIRED`；
- 规则 2：号段取号、库存预扣等"必须独立提交"的短事务用 `PROPAGATION_REQUIRES_NEW` 或 `Db.transactional { }` 模板 DSL（封装 `TransactionTemplate`，见详细设计 §3）；
- 规则 3：只读列表统一 `@Transactional(readOnly = true)` 或不进事务；
- 规则 4：状态流转（支付回调、售后审核）用**条件更新语句**（`UPDATE … WHERE status=?`）做乐观并发，不依赖 `SELECT FOR UPDATE`，保证 H2/MySQL 行为一致；
- 规则 5：事务边界内禁止外部 HTTP（微信/支付宝调用移到事务外，结果落库再进第二个事务），与 PHP 侧现状一致但由代码审查清单固化。

## 8. 横切机制

| 机制 | PHP 现状 | Kotlin 设计 |
|---|---|---|
| 统一响应 | Fractal `{"data":…}` | `ResponseBodyAdvice` 包 `ApiResponse`；错误走 `@RestControllerAdvice` → `{message, errors, code, status_code}` |
| 参数校验 | action 内联 validator | DTO `@field:NotBlank/@Min` 等 + `MethodArgumentNotValidException` 统一转 errors |
| 审计日志 | shoplog/distributorlog 中间件 | `@AuditLog` 注解 + AOP，写 `operator_logs` |
| 接口缓存 | apicache 中间件 | Caffeine + `@Cacheable`（GET 白名单） |
| 定时任务 | everyMinute 扫描（自动取消/成团） | `@Scheduled(fixedDelay=60s)`：订单超时取消、拼团结算、积分过期；多实例用 ShedLock-JDBC |
| 领域事件 | 各 Bundle EventServiceProvider | Spring `ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)`；事件清单沿用：订单已支付/发货/完成/售后状态变更 |
| 异步任务 | 30 个 Bundle 的 Jobs | `@Async` 线程池 + 事件监听；导出、图片处理、通知发送类先进程内队列 |
| 数据脱敏 | datapass 中间件 | VO 序列化 `MaskedString` Jackson 注解（手机号 `****`） |
| i18n | SetLocaleMiddleware + trans key | M0 中文硬编码常量表，key 结构预留 MessageSource |

## 9. 部署架构

单机形态（默认）：

```
ecshopx-boot.jar
 ├─ application.yml（datasource=H2 file / server.port=8080 / jwt secret）
 ├─ sql/schema.sql + seed.sql（spring.sql.init: embedded 首次执行）
 ├─ ./data/ecshopx.mv.db（升级时整文件备份即数据备份）
 └─ ./storage/upload/*（图片本地磁盘，FileStorage 接口预留 OSS/COS profile）
```

Windows/Linux 同 jar 运行；Nginx 反代 + 静态资源分离为可选形态。多实例形态需要 H2→MySQL + Redis 共享 session/缓存，属于 M2 之后的生产化改造，不在本期。

## 10. 风险与决策记录

1. **2199 端点 ≠ 全量重写**：按 P0(≈120)/P1/P2 分层，P2 对接类只做扩展点。已在 URL 列表文档中逐端点标注优先级；
2. HTTP 200-for-all-errors 契约变更可能影响现有小程序拦截器——提供 `ecshopx.compat.force-ok-status=true` 开关在 `ResponseBodyAdvice` 层回退；
3. 源系统个别列名拼写错误（`adrdetail`、`nopost_conf`）**保留原样**，避免双系统并行期数据同步映射成本；
4. 订单/购物车价格计算必须在 service 层单点实现（PHP 里 admin/front 两套 action 各算一份的分裂不允许带入新架构）；
5. MyBatis 选型风险：无 ORM 关联加载，列表页 N+1 靠手写 JOIN/批量按 id 回捞解决——分页工具类必须支持 join count（详细设计 §4.3）。
