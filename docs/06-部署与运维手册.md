# 部署与运维手册（M2-4，docs/04 §29.6 同批交付）

本文是生产化的部署侧文件：首装、旧库迁移、备份/恢复、多实例纪律、压测口径。
代码层面的口径与差异不在本文（docs/04 §29.6），开发过程记录在 docs/05 §M2-4 完成记录。

## 1. 首装

前置：JDK 17+、MySQL 8（`utf8mb4`）、Python 3.8+（只用首装一次）。

```bash
# 1) 方言翻译：schema.sql 是唯一事实源（H2 MySQL 兼容模式方言），MySQL 直跑吃不了
#    CLOB——翻译产物不进 git，部署现场生成
python3 tools/etl_php_to_mysql.py --translate --out-dir /opt/ecshopx/sql
#    产物：/opt/ecshopx/sql/mysql_schema.sql + /opt/ecshopx/sql/seed.sql
#    （脚本会扫描残留的两方言之外写法并报 stderr；本仓库当前 40 处 CLOB 全翻译，无残留）

# 2) 建库（不建表——首跑由应用自己建，schema 全幂等 IF NOT EXISTS / INSERT IGNORE）
mysql -e "CREATE DATABASE ecshopx DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
          CREATE USER 'ecshopx'@'%' IDENTIFIED BY '<密码>';
          GRANT ALL ON ecshopx.* TO 'ecshopx'@'%';"

# 3) 起动
export ECX_MYSQL_PASSWORD='<密码>'
export ECX_SQL_DIR=/opt/ecshopx/sql
export ECX_PAY_KEK='<32字节以上随机串>'        # 见 §5，必配
export ECX_JUSHUITAN_APP_SECRET='<聚水潭入站签名密钥>'  # 批I：全局一把、不分租户；不配则 /api/systemlink/jushuitan/* 一律 sign error
java -jar ecshopx-boot.jar --spring.profiles.active=mysql
#    H2 演示形态（默认 profile）则不需要以上任何一步：java -jar ecshopx-boot.jar，
#    数据在 ./data/，删掉 data/ 即重置演示库。
```

首跑后验证：`GET /api/ping` 200；`operator/admin` 用默认口令登录——**生产首装第一次登录后立刻改密**（源系统 seed 口令是演示值，不是生产值）。

## 2. PHP 旧库数据迁移

```bash
python3 tools/etl_php_to_mysql.py --migrate \
    --old-host <旧库host> --old-db ecshopx_php --old-user ... --old-password ... \
    --new-host <新库host> --new-db ecshopx --new-user ... --new-password ...
```

口径（脚本内 `MAP` 常量）：
- **只搬核心事实**：会员（`ecs_users→members_info`）、商品（`ecs_goods→goods`）、订单（`ecs_order_info→orders`、`ecs_order_goods→order_items`）、交易（`ecs_pay_log→trade`）；
- `trade.order_id` 新库是 **VARCHAR**、旧库是 BIGINT，`str()` 转换写死在搬运行里（§29.6 C241 那条形状差异，判据放一处）；
- 搬进来的历史行一律"**已成交已收货**"固定态（`pay_status=2/order_status=0/is_settled=TRUE`），不在途、不进超时任务、不重算库存——搬家不动新系统的活账；
- 幂等搬运（`ON DUPLICATE KEY UPDATE`），可以反复跑到收敛；
- **配置类表不静默搬家**：运费模板、支付渠道、微信绑定、SystemLink 对接等在新系统有自己的结构与铁律（渠道密钥落库即 AES-GCM 密文，见 §5），要人工重配——映射表是显式的，现场旧库列名不同改 `MAP` 即可。

迁移后核对：各表 `SELECT COUNT(*)` 与旧库对账单核对；订单抽 10 单逐列比对新旧库金额（`order_fee/goods_fee/shipping_fee`）。

## 3. 备份与恢复

**MySQL 形态（推荐生产形态）**：
```bash
# 每日全量 + binlog 增量
mysqldump --single-transaction --routines --triggers ecshopx > /backup/ecshopx-$(date +%F).sql
# binlog 保留窗口 >= 恢复点目标；SHOW MASTER STATUS 记位点与全量互补
```
恢复：建空库 → 导 dump → 用 `mysqlbinlog --start-position` 追到目标时刻 → 起应用。
表规模小（93 张、多为事务流水），dump 秒级；关键是 **binlog 保留窗口要不要掐断**——掐了 binlog，dump 只能恢复到每日一点，丢一天账。

**H2 形态（演示/单机）**：拷 `./data/ecshopx.mv.db`（应用停机时拷，或 `AUTO_SERVER=TRUE` 参数允许另一进程只读）；恢复即替换该文件。H2 文件形态没有 binlog 概念，恢复点 = 上次拷贝点。

恢复演练（每季度一次）：备份文件 → 空库导回 → `--spring.profiles.active=mysql` 起动 → `GET /api/ping` + 抽一个订单详情页面可开。**没演练过的备份不算备份**。

## 4. 多实例纪律

进程无 session 状态（JWT），水平扩展本身没问题；缓存 KDoc 里说的"外置留 Redis 可选项"本批未做，多实例各自缓存的代价可接受（读多写少）。

两条定时任务要只想清楚再开多实例：

| 任务 | 周期 | 多实例风险 |
|---|---|---|
| `StatementSettleJob`（账期生成） | 按各自账期周期 | 各实例按 `statement_no=ST-{类型}-{店铺}-{窗口日}` 撞号幂等，**不重铺**；但白名单 `ecx.schedule.statement-settle-company-ids` 各实例都会跑一遍 |
| `OpenapiStatsFlushJob`（调用量入账） | 每分钟 | 差量并入语义天然支持多实例（UPDATE 累加、UPDATE 算各自差量）；**首行 INSERT 撞 UNIQUE** 时落不进去那份差量改走 UPDATE 再并入一次（不丢账，但多一次 UPDATE） |

推荐形态：**这两个任务在其他实例上用配置关闭或错开**（`initial-delay` 推远 + `company-ids` 按实例分片），不是把"撞了也能并回"当成常态设计——撞号路径里第一次 INSERT 是白写的。

## 5. 密钥与安全

- `ECX_PAY_KEK`：渠道密钥加密的 KEK（`pay_secret_cipher`），**全实例一致、必配**，默认值 `ecshopx-demo-kek` 只在演示库成立。轮换流程：旧 KEK 停实例前把 `pay_channel_config.api_key` 全部解密 → 换 KEK 重启 → 重写全部行（密文带 `enc-v1:` 前缀，没有前缀的行按明文读，堆叠兼容但别把"没加密"当常态）。
- 网关密钥（`openapi_developer.app_secret`）明文存库但只在签对面出（`FORBIDDEN` 黑名单测试钉着不出现）；泄露处置走 `OA-M14` 重置接口，立即生效无宽限。
- 数据库账号上最小权限：应用账号不需要 `SUPER/FILE`，备份账号只 `SELECT + LOCK TABLES`。

## 6. 压测口径

- 基准就是 `OrderStockConcurrencyTest`（50 线程抢 30 件 → 恰好 30 单，Hikari 池 64 上稳定复现）与 `GroupsSeckillConcurrencyTest` 六例；这两个是**功能正确性压测**（不超卖、不多成团），不是 TPS 基准。
- docs/05 打满 64 那条池龄教训的落地：生产 profile 默认 `ECX_MYSQL_POOL=32`（默认 10 会被 50 并发打穿抛 `Could not open JDBC Connection`，被 `catch→false` 误读成业务失败——**并发断言要带失败原因采样**），上量按机不育自调。
- 50 TPS 目标（§29 那句"每秒 50 单"）：单实例 H2 无法给生产数字；MySQL 8 + 32 池 + 索引齐全的 93 张小表，事务路径（下单/结清/账期）单条 SQL 不超过 5 张表 join，属于"需要真链压测才敢报数"的范畴——**线上压测按 §3 备份先行**，先在预发库跑，不拿生产库第一次压。

## 7. 监控最小集

- `GET /actuator/health`（Spring 默认暴露 health/info）：入探活；
- `GET /api/ping`：应用级连通（过 Security 走 permitAll 链）；
- 日志关键字：`openapi 调用量并入 {} 行`（每分钟一次，连续多分钟 0 行说明网关侧没流量或任务死了）、账期任务产单行;
- outbox 堆积告警（批G 起**代码里有面了**）：`GET /api/webhook/backlog`（读码 `webhook.lists`）——待投按出生时刻分桶（`0_6h`/`6_24h`/`24_72h`/`over_72h`）+ 终态 fail 总数；`over_72h` 桶非零或 `fail_total` 持续数百行时人工介入，介入动作**批H 起有批量面了**：`POST /api/webhook/deliveries/replay`（码 `webhook.push`）按 `topic`/`developer_id`/时间段至少一个筛位把终态 fail 最老最先批量置回 pending（缺省 100/上限 500，`reset<matched` 余量分批续；只动 `fail`，`running`/`pending` 不进来）——先给筛位重推一批，`WH-A7` 留给单条疑难；逐条 SQL 手术只在排程卡死时用：
  `SELECT COUNT(*) FROM webhook_delivery_log WHERE status='pending' AND next_try_at < now` 看排程卡死，`WH-A7` 逐条手动重推。
