# kotlin-ecshopx 开发步骤（M0/M1/M2 · P0/P1/P2）

> 版本：v1.0 · 排期依据：[URL 列表 §2/§3](./04-URL列表文档.md) 的优先级分层；里程碑 M 为**工程推进步**，优先级 P 为**功能交付层**，对应关系 M0⇦P0、M1⇦P1、M2⇦P2。

## 0. 总览

```
M0 骨架与核心交易闭环   ── P0 全部功能（≈120 端点：商品→购物车→订单→支付(mock/余额/积分)→会员→后台基础）
M1 完整交易与营销经营   ── P1 功能（售后、券/满减/拼团/秒杀、店铺分销、积分储值、评价、真实微信支付）
M2 生态与长尾对接       ── P2 功能（openapi/ERP/渠道支付族/结算/砍价签到抽奖/其余长尾端点）
验收锚点：每步含"可运行产物 + 测试门槛"，未过门槛不进入下一步。
```

> 已踩坑（2026-10-15 修复）：fat jar + H2 **file** 库组合下 `spring.sql.init.mode: embedded` 会**静默跳过**建表脚本（16KB 空库；同 jar 改 `always` 即建满 70 表；mem 库单测下 embedded 正常，AUTO_SERVER 已排除）。解决：yml 用 `mode: always` + `classpath*:/sql/*.sql`（嵌套 jar 需通配），seed 尾句用 `GREATEST(current_value,100000)` 防止重启回拨号段。验证：空 `data/` 起 jar → 70 表/种子/seq=100000；手工推进号段后重启不回退。

### M0-3 鉴权与租户 —— 已完成（2026-10-15）

范围：AUTH-1..5 五端点（operator login / token refresh / invalidate、h5app new_login / h5app token refresh）、双 SecurityFilterChain（admin 链 `/api/**`、front 链 `/api/h5app/**`）、JWT(HS256, jjwt 0.12.6) + Principal/Kind + TenantContext、@RequiresResource 资源权限切面（admin 类型放行，其余 operator→role→resource 闭包，Caffeine 5m 缓存）、@Audited 审计写 operator_logs、seed 追加 viewer 账号（无角色，越权用例）。

验收：`mvn verify` 全绿 53 测试（含 AuthEndToEndTest 14 项：401/403/400/刷新轮换/跨面拒绝/is_new 语义/审计行数）；fat-jar + 文件 H2 实跑登录→刷新→登出→匿名 401 通过（探针控制器属 test 源集，不进 fat jar，403 语义由 MockMvc 覆盖）。

踩坑（实测）：
1. **Kotlin 切面参数绑定静默失配**：`@Around("@annotation(rc)")` 依赖反射参数名；Kotlin 默认不写 MethodParameters 属性，导致切面永不命中、controller 不代理、越权请求直接 200。修复=切点改全限定名形式 `@annotation(com.ecshopx.kotlin.common.security.RequiresResource)`，方法体内 `MethodSignature.method.getAnnotation(...)` 取注解。
2. **schema.sql 的 `SET SCHEMA ECX` 只是会话级**：连接池其余连接默认 schema 仍是 public，mapper 非限定表名在新连接上报 Table not found。曾试 URL `INIT=...\;SET SCHEMA` —— Spring 属性层吞反斜杠截断 URL（报 URL format error）；H2 2.2 也不支持 `ALTER USER SA SET SCHEMA`。最终方案=部署脚本不再显式建/切 schema，表落默认 public（MySQL 部署选库即等效），BootSmokeTest 断言改 `table_schema='public'`。
3. MockMvc `andReturn().response.contentAsString` 对无 charset 响应按 Latin-1 解码中文出乱码，断言文案一律用 jsonPath（字节级）。
4. Boot 3.3.4（Spring 6.1）无 MockMvc Kotlin DSL（`mvc.post{}/andExpect{}` 为 6.2+），端到端测试用 MockMvcRequestBuilders/ResultMatchers 经典 API。
5. `-java-parameters` 已加入根 pom Kotlin args（对 Jackson/参数名解析有益，切面不再依赖它）。

### M0-4 商品域（GOODS-1..8）—— 已完成（2026-10-15）

范围：后台 GOODS-1 商品列表 / GOODS-2 详情 / GOODS-3 新增 / GOODS-4 更新 / GOODS-5 删除（逻辑下架）/ GOODS-6 SKU 列表，前台 GOODS-7 匿名列表 / GOODS-8 详情聚合（`item_spec_list`、`item_params_list`、`spec_items.custom_spec_id/custom_spec_name`、`cur`、`tdk_data`、`recommend_items`、`tagList`、`member_price`）。配套：`ItemQuery` 入参归一化（元→分、category 展开注入、is_warning 双向、distributor 三态）、`CategoryService` Caffeine 树/平铺双缓存 + 写后失效、`ItemService.enrich` 一次回捞子行/分类/属性/条码/标签/服务标签防 N+1、`@RequiresResource`+`@Audited` 挂 GOODS-1..6。契约侧新增可复用测试框架 `ContractDiff` + `GoodsContract`（字段集抄自 docs/04 §2.2，缺失即失败、多出仅回显）。

验收：`mvn -B verify` 全绿 75 测试（common 14 / dao 12 / service 16 / boot 33；其中 GoodsEndToEndTest 12 项端到端 + ItemQueryTest 10 项归一化单测），JaCoCo common ≥80% 门槛通过。fat jar + 文件 H2 实跑 `tools/m04_smoke.py` 14/14：登录→后台列表(含匿名 401)→新增多规格→后台详情(主行自指 goods_id=default_item_id=item_id)→前台详情聚合→删除→前台 404。契约口径补充见 docs/04 §5（C1..C16）。

踩坑（实测）：
1. **Kotlin `isXxx` 布尔属性与同名裸属性在 JavaBeans 层打架**：`ItemDO` 同时有 `isPoint: Boolean` 和 `point: Long`，Kotlin 给前者生成 `isPoint()/setPoint(Z)`，与后者的 `getPoint()/setPoint(J)` 归并成同一属性 `point`，MyBatis 直接抛 `ReflectionException: Illegal overloaded getter method with ambiguous type for property 'point'`（读写两侧都炸，表现为列表 500 与详情映射把 false 塞进 Long）。修复=`@get:JvmName("getIsPoint") @set:JvmName("setIsPoint")`，Kotlin 侧属性名不变，字节码访问器变 `getIsPoint`，MyBatis 属性名即 `isPoint`，列 `is_point` 经 `map-underscore-to-camel-case` 正好命中。
2. **DO 的 Stampable 必须逐表核对 DDL**：`items_rel_type` 无 `created/updated`、`items_tags` 只有 `created`，照抄 Stampable 会让 seed 与 INSERT 一起报 `Column "created" not found`（spring.sql.init 直接失败→整个 Spring 上下文起不来，报错却埋在 `dataSourceScriptDatabaseInitializer` 里，容易误判成 Mapper 问题）。结论：只有双列齐备的表（items、items_category、goods_items_rel_cats、items_attributes、servicelabels、shipping_templates）才实现 Stampable。
3. **StampInterceptor 的 ParamMap 分支不会凭空造键**：`writeKeys` 仅在字典里已存在 `created/updated` 键时写入，所以 `softDelete(@Param("id"))` 里的 `updated = #{updated}` 是未绑定参数。改成调用方显式传 `TimeSec.now()`（与拦截器同源）。
4. **`updateFull` 不含 `goods_id/default_item_id`**（防止误改挂载关系），于是主行自指必须单独一条 `stampIdentity` UPDATE；漏掉时 `goods_id` 恒 0，`is_sku=true&goods_id=X` 只回子行，看起来像"分页少数据"。
5. **JUnit 5 默认每个 @Test 新建实例**：顺序用例共享的 `itemId` 字段在第二个用例里回到初值 0，连锁产生 `GET /api/goods/items/0 → 404`、`total_count` 对不上等一串假故障。跨用例状态一律 `@TestInstance(Lifecycle.PER_CLASS)`。
6. **500 只回 "internal error" 无从排障**：`GlobalExceptionHandler.onOther` 补 `log.error("unhandled exception", e)`，响应体仍不外泄内部异常。
7. **H2 演示行显式主键后必须抬序列**：`ALTER TABLE items ALTER COLUMN item_id RESTART WITH 100`（含属性/条码/标签/服务标签等 9 张表），否则 GOODS-3 新增撞 PK；MySQL 形态等价改写 `ALTER TABLE t AUTO_INCREMENT = 100`。
8. `spring.sql.init.encoding` 未指定时按 Windows 平台默认字符集读 seed.sql，中文演示数据入库即乱码 → 显式 `UTF-8`。
9. MockMvc 对无 charset 响应按 Latin-1 解码，中文断言统一走 `String(contentAsByteArray, UTF_8)` 或 jsonPath；测试登录体一律 `mapper.writeValueAsString(mapOf("password" to pw))` 构造。

4. **`kotlin.test.assertEquals(Int, Long)` 静默走 `assertEquals<Any>`**：`asLong()` 返回 `Long` 而字面量是 `Int`，编译通过、运行时按对象比较必失败，报"expected 1 actual 1"这种看不出差别的错。全文件 grep 审一遍，数量/金额断言统一写 `0L/1L`；`jdbc.queryForObject(..., Long::class.java)` 返回可空，Kotlin 侧必须 `!!`（否则 `Return type mismatch` 与"nullable receiver 禁止运算符调用"连锁报错）。
5. **期望值要按 seed 实际口径算**：坚果礼盒的 `goods_id` 是 3（不是 1）、`sales` 基线 30、`order_id DESC` 排序后"最新一条"是刚被取消的车内下单单而非 orderA —— 三处断言都是先跑一遍读出真值再改测试，而不是猜。
6. **自证式断言是负债**：初稿写过 `assertEquals(x, x)` 形态的"占位不保持等式"和一个两边都含 `store()` 的库存等式，看着严谨实则零信息量（还引入 Int/Long 歧义）。库存账最终改成两条 JOIN 聚合：`store = 200 - 未取消件数`、`sales = 30 + 未取消件数`，外加"已关闭单满足 `cancel_item_num = num - delivery_item_num`"。
7. **实跑脚本对脏库敏感**：`tools/m04_smoke.py` 在复用的文件 H2 上第二次跑会 400/500 —— GOODS-5 是逻辑下架，残留行仍在 `items`，而 H2 演示行 `RESTART WITH 100` 后自增基址不随重启推进，新建商品直接撞 `PRIMARY KEY ON items(item_id)`。结论=**实跑前先清 `data/*.db` 让 seed 重放**（脚本另加"按 `item_bn` 预清理"作为兜底），MySQL 侧无此问题（`AUTO_INCREMENT` 持久推进）。
8. **超时实跑需要两处联动**：`auto_cancel_minutes` 属 `sys_config`（非 JVM 属性），要让它"建单即到期"只能在服务停机时用 H2 工具改库（`UPDATE … SET config_value='0'`，seed 是 `INSERT IGNORE` + 唯一索引 `uk_cfg_key`，重启不会被覆盖），再以 `--ecx.schedule.order-timeout-initial-delay-ms=1000 --ecx.schedule.order-timeout-ms=2000` 启动；`INIT=…` 拼在 URL 上的写法不可用，因为 `spring.sql.init` 在连接建立后才跑 seed，UPDATE 会先于 INSERT 而落空。

6. **实跑脚本的位置参数陷阱**：`fail(method, path, body, code, token)` 里按 `req` 的习惯把 `atok` 传成第 4 位，等于 `code=atok`、`token=None` → 后台发货 401「Unauthenticated.」；凡是"看起来同构"的助手，跨模块复用时一律用命名参数或退回 `req`。同轮还集中暴露 `pay_status` 的字面量是 `NOTPAY` 而不是想象中的 `UNPAID`（5 处断言一起红）。

踩坑（实测）：
1. **`@Param` 必须显式命名**：Kotlin 里写 `fun clearDefault(@Param("userId") Long)` 直接报 `An explicit type is required on a value parameter`（不是"缺名字"而是被解析成带注解的类型片段），一处报错误导整片文件。批量补名后用 `grep -rn '@Param("[a-zA-Z]*") [A-Z]'` 兜底扫全仓，零命中才算完。
2. **SQL 引用 `#{created}` 就必须实现 `Stampable`**：`MemberAddressDO` 声明了 `: Stampable` 却没写 `override var created/updated` 编译不过；反过来 `SysConfigDO`/`UploadFileDO` 的表根本没有 `created` 列（只有 `updated`），但仍要实现接口——因为 `StampInterceptor` 只给 `Stampable` 对象盖时间戳，字段存在而 SQL 不引用它即可。判据是"SQL 里出现 `#{created}`/`#{updated}` ⇒ DO 必须 `Stampable`"，而不是"表有没有这列"。
3. **KDoc 里的 `/storage/**` 第三次踩嵌套注释**：`/**` 在 Kotlin 块注释里会**再开一层**（块注释可嵌套），编译器只给 `Unclosed comment` 并指向文件末尾。三次复发（M0-5、M0-7、M0-8），已在 C81 里写成"prefix 通配"。
4. **`-pl` 不带 `-am` 用 `~/.m2` 的旧 jar**：`mvn -pl ecshopx-boot test` 里新增的 12 条端点全部 404，因为 reactor 只有 boot 一个模块，`ecshopx-web-front` 取的是本地仓库里上一个 install 的 jar。先 `mvn -B -DskipTests install` 再跑单模块，或一律带 `-am`（README 已把这条写进常用命令）。
5. **fat jar 运行时不能 `verify`**：Windows 下运行中的 jar 被 JVM 锁住，`spring-boot:repackage` 报 `Unable to rename … .jar.original`。测试其实已全绿（145/145），只是打包阶段失败；先停服再跑构建，别把这条当成回归。
6. **实跑断言要"只前进不回退"**：`system.is_saas` 的默认行在 `company_id=0`，SUP-1 冒烟写一次就产生租户覆盖行——第二次跑"全局层可读"必然失配（读到的已是租户行）。改成两断言：合视图同键**只出一条**（与状态无关）+ 用一条**接口永远写不到的全局专属键**证明全局层可读（seed 追加 `site.member_center_copy`）。同类问题在足迹用例上表现为"匿名浏览"其实带了会员令牌、把足迹写进了人名下——脚本自身的 token 漏传/多传要用"前后总数差值"来兜住，而不是绝对值。
7. **URL 里的中文查询参数要百分号编码**：`?keyword=坚果` 直接拼进请求行，`http.client` 用 ascii 编码 header 时抛 `UnicodeEncodeError`。`urllib.parse.quote(path, safe="/?=&:%")` 统一在 `req()` 入口做一次，避免每个用例各自记得。

踩坑（实测）：
1. **`consumes` 分流在空 body 上必然歧义**：`/api/notify/wxpay` 想按 `consumes` 拆 JSON 与表单两条映射，`curl -X POST`（不带 body）会同时命中两条 → `IllegalStateException: Ambiguous handler methods` → 500，而 500 的应答体不是渠道认识的格式，渠道按服务端故障无限重试。改成**只注册一条映射、按报文本身（`{` 前缀）分流**。`MockMvc.param()` 发的表单也是空 body，测试里同样撞得上——这条是 M1-2 第一个真炸出来的契约坑。
2. **控制器往回调参数 map 里塞 `channel`，把支付宝真通知全灭**：渠道签名覆盖"收到的全部参数"，多一个键就永远验不过；表现是 6 例下单相关的用例统一回 `failure`，而 `formAck` 又把失败原因（`回调验签失败`）盖掉，HTTP 面完全看不出错在哪。修成渠道身份走独立入参、**验签之后**才补进结清参数（C98）。教训：排障时绕开应答体，直接 `@Autowired PayService` 调 `notifyForm` 打 `NotifyResult.message`。
3. **支付宝 4.39.x 的公共参数在 URL query**：`method`/`sign` 挂 query、body 只剩 `biz_content`，而待签串是两处合并的全参数。假网关只读 body 时 `method` 取空 → 应答拼成 `{"_response":…}` → SDK 找不到节点 → 报"**待验签内容不可为空 content=null**"，这条异常信息一个字都不指向"你没读 query"。先用 JDK `HttpServer` 的 `requestURI.rawQuery` 把请求形态打出来，再决定怎么合参数（C100）。
4. **应答的签名对象是节点那段子串，不是整个 body**：`JsonConverter` 用 `indexOf(api_key)+长度+2` 定位、花括号配对截断，把原文交给 `SignChecker`。夹具必须"先拼节点文本 → 对节点签名 → 再套外壳"，顺序反了就必然验不过；这类规则只能从 bytecode/实测拿，文档写的"对响应 JSON 签名"不够精确到 substring（C99）。同类坑：`isSuccess()` 只看 `sub_code`（不看 `code=10000`），夹具的成功节点里一个 `sub_*` 字段都不能有（C101）。
5. **渠道原话不归一化 = 掉单永远补不上**：`queryTrade` 直接把 `TRADE_SUCCESS` 传回去，补单作业的判据是 `trade_state=="SUCCESS"`，报文完全正常、账却不动。归一化收敛到一个 `normalizeStatus`，回调与查单共用（C102）。改这个方法时顺手撞出 Kotlin 类型坑：`String?→String?` 让 `mapOf` 推断成 `LinkedHashMap<String,String?>` 与返回类型 `Map<String,String>?` 不匹配，判据改成非空入非空出、可空性只留在 `?.let(::normalizeStatus)` 一处。
6. **删了临时排障测试的源文件，旧 class 还会被跑到**：`AliProbeTest.kt` 删掉后 `mvn verify` 仍以 `NoSuchMethodError: SimAliPayServer.getProbeDump()` 失败——`target/test-classes` 里的陈旧 class 不会被 Kotlin 增量编译清掉。要么 `mvn -B clean verify`，要么手工删对应 class；别把这条当成产品回归。
7. **冒烟脚本不能照文档猜路径**：`/api/offline-payments/order/{id}` 在实现里根本不存在（审核面只有 `list`/`check` 两条，`?order_id=` 就是钻取），照 §13 之前的直觉写会拿到 404 后被 `data()` 的 assert 直接崩掉；`viewer` 在 seed 里**不挂任何角色**，"只读账号能看待审列表"这种想当然的断言也是错的（实际 403）。写冒烟前先读 controller 与 `seed.sql`，别读设计文档。
8. **七脚本同库顺序跑的"残单"不变式互踩**：m07 断言会员的待付款单归零，而 m12 的失败回调/驳回凭证**本该**把单留在 `NOTPAY`，且 m11 刻意留一笔未支付单验"未付款不能申请售后"。m12 收口改为进场记基线、退场断言回到基线（D21）——全局归零式断言只能单跑成立，顺序回归里必然误报。
9. **jar 在跑就不能 `verify`**（第 6 次踩）：`spring-boot:repackage` 报 `Unable to rename …jar.original`；跑构建与跑实跑必须分先后。另有一条同族坑：`mvn test -pl ecshopx-boot` 用的是**已安装**的同模块产物，改了 dao/service/web 必须先 `mvn -B -DskipTests install`，否则测的是旧 jar——本轮 `install` 一次 + `clean verify` 一次才把两条一起收敛。

踩坑（实测）：
1. **一条 `VARCHAR(16)` 把三个用例打死成"act_id 必填"**：seed 建表时 `seckill_type VARCHAR(16)`，而本项目用列值表达类型，`limited_time_sale` 正好 17 个字符 → H2 `Value too long for column`。表现完全指不到列宽：写库失败让 `save()` 返回的活动 id 是 0，下游 `/activities/0/goods` 一律 404，前台用例则拿到"act_id 必填"的 400。教训：**新枚举值进老列之前先数一遍字符长度**，别只看"能不能编译"（schema 末尾追加 `ALTER COLUMN … SET DATA TYPE VARCHAR(32)`，MySQL/H2 同一语句可跑）。
2. **`horizon` 是提前量不是绝对时刻**：机器人扫描写成 `t.end_time <= #{horizon}`，`runNow()` 永远返回 0 —— 不报错、不失败，只是"机器人从来不凑团"。正确判据 `now < end_time <= now + horizon`（C131）。这类"窗口条件写反"的坑只能靠一条**正向用例**兜：本案专门造一个 5 分钟结束、允许机器人的 3 人团，断言 `fillRobots()` 真的补出 2 个 `user_id<0` 的行并把团推到 2。
3. **未知类型码静默降级比报错危险**：`activity_type=7` 原本落进 `when` 的 `else` 分支被当成"普通秒杀"建出来了（200 + 一条不该存在的场次）。改成 `seckillTypeOf` 未知码返回空串、交给 `validate()` 报 400「只支持 normal/limited_time_sale」——**"两个写法都收"不等于"什么值都收"**（C126）。
4. **断言的模型必须来自代码，不是来自对业务的想象**：本轮两处自我修正都是这个性质。①"已付成员行在判失败时会被清掉"——实际 `failTeam` 只删未付行，已付行留着做对账（C128），断言从"成员行归 0"改成"成员行保留且再跑一轮结算不复活、不重复退款"；②`available` 是**算出来的**列（总 − 已售 − 占用），`SELECT available FROM promotions_seckill_rel_goods` 直接 BadSqlGrammar，`report()` 的 `available_store` 又是全场次求和（C124），行级与单级两个数别混。
5. **`created` 与 `create_time` 两套命名在同一个库里并存**：`orders_normal_orders` 的列是 `created`（StampInterceptor 维护），出参才叫 `create_time`。冒烟里连库的 SQL 写 `create_time` 就炸，写 `created` 才对——这类"列名 ≠ 出参名"的地方一律先读 `OrdersMapper` 的列清单再落笔。同类：`trade` 表的判据列是 `trade_state`，重放幂等断言要查 `COUNT(*) WHERE trade_state='SUCCESS'` 而不是看 HTTP。
6. **重复支付与重放回调是两件事**：想验"结清不双计"，第二次调 `PAY-2` 只会拿到 422「订单已支付」（正确行为），什么都照不出来；要往 `/api/notify/wxpay` 再发一条同 `out_trade_no` 的**表单报文**，看它仍答 `SUCCESS` 而 `hold_store/sales_store` 一动不动（C127）。e2e 里因为已经有 `notifyWx()` 夹具，顺手把 `pay()` 拆成"建支付单 + 回调"两步，重放直接复用夹具。
7. **跨会员的支付要换令牌**：`payment` 是会员面端点，用团长令牌给第二个会员的单付款拿到的是 403——而 403 之后那个团的人数与额度账目全线走样，红的是三条之外的用例。冒烟与 e2e 都改成 `pay(orderB, tok=otok)`（同族：`order_new` 的收货信息，会员 2 在演示库里没有地址行，`address_id=1` 会 422「收货地址不存在」，走明文六件套那条腿才对）。
8. **邻居脚本的残单会踩自己的"归零"不变式**（第 9 次记这条，本轮又换了一种形态）：`m07` 收尾断言"会员待付款单必须为 0"，而常驻库里 m11 刻意留一笔未支付单验"未付款不能申请售后"，九脚本顺序回归时 m07 必红。改成进场记基线、退场回到基线（docs/04 §16.3）。同族但**不放宽**：m07 的"余额不足 422"依赖 `user_deposit` 的绝对值，脚本 docstring 第 10 行早写明"服务需以干净库启动"，本轮实测脏库第二轮它确实会假绿（余额被上一轮充值抬高 → 不足分支走不到），因此九脚本的顺序回归**仍以清 `data/` 为准入门槛**，不是可选项。
9. **jar 在跑就不能 `verify`**（第 7 次踩）：`clean` 删不掉被 JVM 内存映射的 jar，`repackage` 又报 `Unable to rename …jar.original`。实跑冒烟与跑构建必须分先后；本轮还多一条同族流程：改了 dao/service 之后跑实跑，得先 `install` 改动模块再 `package -pl ecshopx-boot`，否则 18080 上跑的是旧产物（本轮 `team_id` 出参就是这么"改了没生效"的）。

1. **`SK-A6` 圈品是 `PUT`，用 `POST` 打过去 405 而且报文一点线索都不给**：新写的并发用例借了冒烟里的 `adminOf()` 助手，它固定发 `POST`，于是"创建成功、圈品 405、下游全线红"。教训：助手函数一旦被两个以上端点复用，**方法就得成参数**（补 `m: String = "POST"` 分流 + `put` 的 import），别在调用方外面拼 URL 猜。
2. **矩阵的两个失败都不是测试写错，而是生产 bug**：①`满 140 元可用，当前 69.08 元`——门槛判据在满减之后、积分之前，而文案在链跑完后重算，把已经够得着的 138.15 报成积分后的 69.08；先怀疑判据、独立探针对比 `coupon_reason` 与 `oracle()` 才发现**判据完全正确、只有文案错**，于是改用"当场记因"而不是"把基数再加回去算"（后者永远差积分这一步，C134）。②`ORDER-5 的 discount_info == []`——e2e 全绿、只有实跑炸，因为用例此前不断言这个字段；用独立 Python 探针复现"满减单 `discount_fee=3000` 而构成空"才定位到 helper 用错（对象数组列 vs 字符串数组列，C137）。**这两条一起说明：矩阵这种"多开关全组合"的用例，价值在于它会逼出单点用例永远碰不到的分支组合。**
3. **拒单文案有两条路，断言写死一条就红**：串行下单被 `OrderCreateService` 的 `available` **预检**拦下报「活动名额不足」，临界并发穿过预检后才被 CAS 拦下报「已被抢完 / 名额已用完」（C136）。并发用例的"再多一笔"断言因此放宽为 `名额|抢完` 子串——**放宽的是文案匹配，不是行为**：单数、池子、额度三个数照旧精确断言。
4. **冒烟脚本不能连库，等级与余额只能"读出来"**：e2e 用 `UPDATE members SET grade_id=3` 切金卡，脚本没这条路，改用**两个会员分别登录**（普通会员 / 金卡，积分余额 1000 与 500）各持一张券，每格从 ORDER-1 的 `user_point` 实时取余额再喂 `oracle()`。**积分余额决定哪条钳制分支被压到**：矩阵每格都该由比例钳住（余额给足），余额钳那条路 #56 的 Order 9 已单独验过，本轮不必也不该重复（D40）。
5. **满减没有"只改开关"的端点**：编辑必打回重审（审核闸门），矩阵切"满减开/关"只能 `POST`+`PUT /check` 与 `DELETE` 两次调用。因此**每格必须自己开关、循环进场先复位**——上一条用例漏删的残档会污染后面 15 格的基数，表现是"只有第 7 格红"这种最难读的失败（D41）。
6. **`Int`/`Long` 装箱让 `assertEquals(0, hit.sum())` 永远不等**：`transit()` 返回 `Int`、`race()` 回 `List<Int>`，`sum()` 是 `Long`，`assertEquals(0, …)` 比的是 `Integer(0)` 与 `Long(0)`，`equals` 直接 false。并发断言一律写 `0L`/`1L`（同族：`jdbc.queryForObject(…, Long::class.java)` 的计数也要 `2L`）。

1. **账实相符是坐标系问题，不是断言问题**（C185）：常驻库上历史行不为零，绝对式 `Σ == point` 从第一次动账起就注定是红的，于是两边都写成**差值**（进场记 `(point₀, Σ₀)`，此后只断 `point − point₀ == Σ − Σ₀`），储值因 seed 是 0/0 才允许用绝对式。判据的密度也是设计：**每动一次账就把两条恒等式各过一遍**（冒烟 12 组、e2e 每段一次），而不是收尾只查一次——收尾才查等于把"哪一步开始不对"这个最有用的信息扔掉了。`point_member_log` 没有唯一键，seed 的 `INSERT IGNORE` 在常驻库上每启一次多插一份，所以本批**故意不给它配种子行**，起点因此是干净的 0。

### M2-4 生产化（批F：§87 承诺收口——MySQL + 账期出账 + 渠道密钥加密 + D76 聚合入账）—— 编码收官（2026-10-23）

实现要点：

1. **结算事实源只有一条，算式一次收口**（C241）：`trade.is_settled=TRUE AND trade_state='SUCCESS'`，窗口按**结清时刻**（回调 CAS 结清写的 `trade.updated`）；退款取 `refunded_fee`，运费/佣金回 orders 补（`OrdersMapper.listStatementFees`）；应结 = 实付 − 退款 − 平台佣金，**推广佣金（total_rebate）单列不复扣**。"一单一生"的去重判据放 **Kotlin** 不放 SQL——`trade.order_id` 是 VARCHAR、`statement_details.order_id` 是 BIGINT，JOIN 强转在 H2/MySQL 两方言写法不同，判据进服务层一处；生成幂等靠 `statement_no=ST-{类型}-{店铺}-{窗口日}` 撞号不重铺，任务腿与 e2e 直调 `generate` 是同一条（不开测试专用口）。
2. **打款位不做**（C242）：确认只推 ready→confirmed 一格；`confirmed→paid` 要接财务回单，没有回单就置"已付"等于凭空宣布付过钱。**账期单由任务生成，接口只读/只确认**（C243）：运营侧没有"手动出账"口子。**本批只跑 distributor 账位**（C244）：supplier 设置行建了、位次留着，但本项目订单链上 `supplier_id` 恒 0，没有可对账事实源——有据才出账。
3. **调用量聚合是"并入"不是"消费"**（C246）：`drainTo` 把【当前值−上次基线】的**差量**交给任务，进程内读口（OP-A6 的 gateway 三位）语义不变；闸门就失败的 UNKNOWN 桶认不出租户、**不入租户账**。任务侧 UPDATE 累加天然支持多实例（各并各的差量），首行 INSERT 撞 UNIQUE 时把差量改走 UPDATE 再并入一次（不丢账）。OP-A6 变三个数字组：`gateway`（进程内）/`delivery`（webhook_delivery_log）/`aggregate`（openapi_call_stats，是账），note 写明不同源——混成一个"总调用数"就没人知道哪一半是估的。契约同步 `OpenapiContract.STATS/STATS_AGGREGATE`，M21 门槛⑤补子契约断言。
4. **密钥加密收口在服务层，不在 mapper**：`PayChannelConfigService` 写侧 encrypt/读侧 decrypt 成对出现，三家 JSON 渠道（`JsonTradeChannel`）全部改走服务层——签名/验签用的是**明文原值**（判定层永远读原值，MASK-R1 同律），掩码（`Mask.secret` 前4后4）只发生在后台出参。形态 `enc-v1:{iv}:{ct}`、AES-256-GCM、KEK 由 `ecx.pay.kek` SHA-256 派生（部署注入，全实例一致；默认值只在演示库成立）；**兼容判据**：没有前缀按明文读（老行/e2e 直插假密钥照跑），加密上线不停机不改表；解不开按原样返回不抛——宁可签名失败也不 500。`api_key` 空串=不改（改开关不抹密钥）。
5. **MySQL 面不另存一份 DDL，也不假装 schema.sql 能直跑**：业务 SQL 在 M0 起就写在两方言交集上（`<script>/<if>`、`LIMIT #{offset} #{limit}`、内联 `AUTO_INCREMENT`、`INSERT IGNORE`），唯一方言差是 CLOB——ETL `--translate` 一次性生成 `mysql_schema.sql`（产物不进 git，schema.sql 仍是唯一事实源），profile 指向 `ECX_SQL_DIR` 下的产物。ETL `--migrate` 只搬核心事实（会员/商品/订单明细/交易），'已成交已收货'固定态不动活账，`trade.order_id` VARCHAR 形状差异写死在搬运行里。
